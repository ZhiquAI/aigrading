## 1. 总体评估结论

**核心观点**：方案愿景先进，架构理念符合行业最佳实践，但**不能直接替换**现有代码。需采取**"扩展适配" (Extend & Adapt)** 策略，在保留 V3 Schema 的基础上引入新特性。

| 维度 | 评分 | 评价 |
|------|------|------|
| **架构设计** | ⭐⭐⭐⭐⭐ | "配置驱动 + 工厂模式" 是解决 K12 多学科复杂度的正确方向。 |
| **创新性** | ⭐⭐⭐⭐⭐ | "教师个性化规则注入" (Custom Rules) 是极具价值的差异化功能。 |
| **兼容性** | ⭐⭐ | 数据结构设计与现有 V3 Schema (`rubric-v3.ts`) 严重冲突，缺乏迁移路径。 |
| **落地难度** | ⭐⭐⭐⭐ | 需在 Prompt 工程和前端组件上投入较大精力，但技术路径清晰。 |

---

## 2. 方案亮点 (Highlights)

1.  **架构理念清晰**：
    -   **Backend as Brain**: 通过 `PromptFactory` 动态生成 AI 指令，避免了硬编码学科逻辑。
    -   **Frontend as Face**: 通过 `AdaptiveUI` 根据数据类型自动切换渲染组件，实现了 UI 的解耦。

2.  **数据协议设计合理**：
    -   引入 `ui_type` (render hint) 和 `match_mode` (logic hint)，让评分细则具备了"自描述"能力。

3.  **"教师规则注入" (Killer Feature)**：
    -   允许教师用自然语言（如"字数不够扣分"）干预评分标准，填补了通用 AI 与个性化需求之间的鸿沟。

---

## 3. 风险与问题 (Risks & Issues)

### 3.1 数据结构冲突 (Critical)

| 现有实现 (V3 Schema) | 重构方案建议 | 冲突分析 |
|----------------------|--------------|----------|
| `strategyType` (计分逻辑) | `ui_type` (渲染逻辑) | 关注点不同。V3 关注"如何算分"，方案关注"如何显示"。 |
| `point_accumulation` | `badge`, `checklist` | 方案试图用 UI 类型替代逻辑类型，会导致后端计分引擎失效。 |

**风险**：直接采用方案会导致现有数据库数据不可用，且需重写计分引擎。

### 3.2 学科配置维护成本高
方案建议维护一份巨大的 `SUBJECT_CONFIG` 映射表（学科 -> 题型 -> 策略）。
**风险**：K12 题型千变万化，硬编码维护成本极高，且容易覆盖不全。

### 3.3 性能隐患
方案建议引入 `react-latex-next` 进行公式渲染。
**风险**：MathJax/KaTeX 类库体积庞大 (~300KB+)，直接引入会显著增加 Chrome 扩展的包体积，影响加载速度。

## 4. 实施建议 (Recommendations)

### 4.1 核心策略：融合而非替换

不废弃现有的 `rubric-v3.ts`，而是将方案中的新字段作为**扩展属性**引入。

```typescript
// 建议的融合 Schema
interface RubricPoint {
  // 原有 V3 字段
  score: number;
  content: string;
  
  // 新增扩展字段 (Optional)
  uiHints?: {
    type: 'badge' | 'formula' | 'checklist'; //以此指导前端渲染
    icon?: string;
  };
  logicHints?: {
    matchMode: 'exact' | 'semantic';      // 以此指导 AI 匹配
    customRuleId?: string;                // 关联的教师规则
  };
}
```

### 4.2 简化学科配置
采用 **"轻量级配置 + AI 自动推断"** 策略：
- 前端只提供基础的学科列表。
- 将识别题型（填空/简答/作文）的任务交给 AI，而非用户手动选择。

### 4.3 分阶段落地路线图

1.  **Phase 1 (后端核心)**：
    -   实现 `PromptFactory`，支持 `custom_rules` 参数。
    -   扩展 V3 Schema，增加 `uiHints` 字段。
2.  **Phase 2 (前端交互)**：
    -   改造向导页，增加"高级设置"面板（输入个性化规则）。
    -   对接新 API。
3.  **Phase 3 (UI 升级)**：
    -   实现多态渲染组件。
    -   按需加载 LaTeX 渲染引擎（如有必要）。

---

## 5. 结论

重构方案方向正确，尤其是"个性化规则"功能将显著提升用户体验。建议立即启动 **Phase 1 & 2**，优先打通"教师输入规则 -> AI 生成细则"的链路，暂时搁置复杂的 LaTeX 渲染，确保系统稳定性与兼容性。
